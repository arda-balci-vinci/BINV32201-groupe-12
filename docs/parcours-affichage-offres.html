Gesta / documentation technique

Du composant React à la base de données

Ce document retrace le parcours de GET /offers, depuis la page React jusqu'aux tables SQLite, puis le retour des données vers le tableau affiché. Il indique aussi les fichiers à prévoir pour ajouter un filtre par période.

Architecture générale

Frontend React

Les pages composent les hooks et les composants. Les hooks chargent un état prêt à afficher ; les services HTTP valident les réponses ; les modèles décrivent les données de l'API.

API Express

Les middlewares authentifient et autorisent la requête. Le contrôleur reste mince, le service porte les règles métier et le repository porte le SQL.

SQLite

Les migrations définissent le schéma. Une offre référence une entreprise, une année académique et une période ; les jointures reconstruisent la ligne nécessaire à l'API.

Le flux backend est donc : controller → service → repository → SQLite. Au retour, les mappers transforment les lignes SQL en objet métier puis en DTO public. Voir docs/architecture.md.

Parcours détaillé de l'affichage

1

La route React est rendue

frontend/src/App.tsx affiche OffersPage pour /offres si canListOffers(user) l'autorise côté interface. Le backend reste l'autorité finale.

2

La page lance le hook

frontend/src/pages/OffersPage.tsx appelle useOffers(token, onUnauthorized). Il gère chargement, erreur, résultat vide et rendu de OfferTable.

3

Le hook appelle le service

frontend/src/hooks/useOffers.ts utilise un AbortController et appelle frontend/src/services/offers.service.ts. Le service envoie le jeton directement dans Authorization, sans préfixe Bearer.

4

Vite relaie la requête

frontend/vite.config.ts relaie /api/offers vers l'API (port 3000) et retire le préfixe /api. Express reçoit donc GET /offers.

5

Express authentifie et autorise

backend/src/app.ts branche authenticate avant le routeur. Le middleware relit l'utilisateur en base à partir du jeton. Puis backend/src/controllers/offers.controller.ts applique authorize(canListOffers).

6

Le service choisit la visibilité

backend/src/services/offers.service.ts construit le filtre selon le profil : toutes les offres pour un administrateur, les offres PUBLISHED pour un étudiant, ou les offres du déposant pour un contact autorisé.

7

Le repository exécute SQL

backend/src/repositories/offers.repository.ts lie les tables offers, companies, academic_years et periods. Il applique les filtres de visibilité et trie par année académique puis date de création.

8

Les données remontent vers React

backend/src/mappers/offer.mapper.ts transforme le DBO en modèle puis en DTO. Le service frontend vérifie le JSON avec un type guard. Enfin frontend/src/components/OfferTable.tsx affiche le titre, l'entreprise, l'année, la période et le statut.

Correspondance avec la base

offers.period_id
  └── periods.id
        ├── periods.code              → OfferDto.period (P1 | P2 | OTHER)
        └── periods.academic_year_id
              └── academic_years.id   → OfferDto.academicYear

Le schéma est défini dans backend/src/db/migrations/001_initial.sql. La contrainte de clé étrangère composite garantit que la période appartient bien à l'année académique de l'offre. Les codes restent en anglais dans l'API et le stockage ; les libellés d'interface sont définis dans frontend/src/utils/labels.ts.

Ajout d'un filtre par période

Une implémentation cohérente ferait voyager un paramètre facultatif, par exemple GET /offers?period=P1, jusqu'au repository. Le filtre ne doit pas remplacer les règles de visibilité existantes : il doit s'ajouter à celles-ci.

Fichier Rôle dans le changement
frontend/src/pages/OffersPage.tsx Ajouter le contrôle de sélection ou recevoir la période choisie, puis la transmettre au hook.
frontend/src/hooks/useOffers.ts Ajouter la période aux paramètres du hook et à ses dépendances d'effet pour recharger lorsque le choix change.
frontend/src/services/offers.service.ts Construire le query string encodé et appeler /offers?period=....
frontend/src/models/offer.ts Réutiliser PeriodCode et PERIOD_CODES pour typer les valeurs acceptées.
frontend/src/components/OfferTable.tsx (si nécessaire) À modifier seulement si le contrôle de filtre est placé dans ou près du tableau.
backend/src/controllers/offers.controller.ts Lire et valider le paramètre period ; refuser les valeurs inconnues avec INVALID_QUERY.
backend/src/services/offers.service.ts Ajouter le critère de période au filtre tout en conservant la visibilité liée au profil.
backend/src/repositories/offers.repository.ts Étendre OfferFilter et le WHERE SQL pour filtrer p.code ou o.period_id.
backend/src/models/offer.ts Probablement inchangé : PeriodCode existe déjà ; à vérifier si le contrat d'entrée devient un type partagé.
backend/API.md Documenter le paramètre, les codes autorisés et l'erreur de validation.
backend/http/offers.http Ajouter des exemples de requêtes filtrées, si les scénarios REST Client sont maintenus.
backend/tests/offers.test.ts Tester chaque période, une valeur invalide et la combinaison période + visibilité par profil.
frontend/tests/OffersPage.test.tsx Tester l'interaction du filtre, la requête envoyée et le rendu de la liste filtrée.

Aucune nouvelle migration n'est nécessaire pour ce filtre : la table periods et la relation avec offers existent déjà.
